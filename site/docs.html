Use TENET in Pi.

TENET evaluates eligible tool calls against an owner-written policy. Start in observe mode, then decide whether to enable blocking.

Set up a local checkout

Clone the TENET source into a directory you'll keep. Install its dependencies, then add it as a Pi package:

git clone https://github.com/koenvg/Tenet.git "$HOME/Tenet"
cd "$HOME/Tenet"
bun install --frozen-lockfile
pi install "$PWD"

Set TYPESAFE_API_KEY using your normal secret manager. Put a TENET.md policy in the Pi session's working directory, or set TENET_POLICY to an absolute path. Start Pi and run /tenet status. Without a local or selected policy, TENET is dormant.

Write a rule

Policies are plain text. A blocking rule can describe when approval is needed:

Rule; BLOCK; Never publish code to a remote repository without explicit approval.

Rules are evaluated individually. The assessment may be wrong or unavailable, so review findings and test a policy before relying on enforcement.

Observe or enforce

Observe is the default. It reports findings to the owner, but never vetoes a call or opens an approval prompt. Use /tenet to review recent findings.

Enforcement needs an explicit new Pi process with TENET_MODE=enforce. BLOCK rules may stop a call or ask for native approval. WARN rules remain advisory. An unavailable assessment is not an all-clear.

Records and limits

In eligible sessions, TENET saves submitted assessment evidence locally by default, including passes. It may contain source code or secrets. Set TENET_RECORDING=off before starting Pi to opt out of new capture. Old records remain until you remove them separately.

TENET assesses tool calls exposed to its Pi extension. It does not inspect subprocesses or provide an OS sandbox. Semantic judgments are fallible, and reporting can fail. It cannot guarantee complete coverage or safety.
