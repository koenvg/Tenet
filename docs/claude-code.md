# Claude Code hook prototype (host verification blocked)

This is an opt-in local CLI hook and Unix socket bridge for macOS/Linux. It is **not a verified enforcement integration**. No Claude Code binary was available on this machine during implementation, so no version can honestly be pinned as tested. Offline fixtures cover the protocol and scripted decisions; they do not prove the host runs hooks, preserves denial, or correlates results as expected. Do not rely on this for unattended publishing.

## Try it in an isolated installation

1. Use a private directory without symlinked ancestors. By default the bridge creates `~/.tenet/claude` with mode `0700` and a `0600` socket and session-state files. The parent `~/.tenet` contains the existing shared control file. Set `TENET_CLAUDE_DIR` to an absolute private directory if needed; use the same environment for the bridge and hooks. `TENET_MODE` must also match on both sides. Start in `observe` (the default). Put `TENET.md` in the Claude session's working directory, or set an explicit `TENET_POLICY` relative to that directory. The production judge needs `TYPESAFE_API_KEY` in the bridge process; no hook reads that key from tool input. The bridge records submitted assessment evidence by default in `~/.tenet/recordings`, including passes, even in observe mode. Set `TENET_RECORDING=off` in the bridge process before starting it to opt out; changing the hook client's variable alone does not disable bridge capture.
2. Start the bridge yourself: `bun /ABSOLUTE/TENET/src/claude/cli.ts bridge`. It does not daemonize. Stop it with Ctrl-C. A leftover socket after a crash must be inspected and removed manually with the bridge stopped. The bridge will not replace an existing socket.
3. Copy [the example hook settings](claude-hooks.example.json) to a **separate** Claude settings file, replacing both absolute placeholders with actual paths. The command uses synchronous hooks. `PreToolUse` has no `matcher` and no `async`, so built-in and MCP tool names use the same path. No owner settings are edited by Tenet. Do not add other argument-mutating hooks and claim assessed arguments are stable. Test with a disposable project and isolated Claude settings before considering owner settings.
4. Remove the entries from your isolated settings and stop the bridge to uninstall. This removes interception; it does not remove old recordings or the shared control state. To discard test session markers, stop Claude and the bridge first, then inspect and remove the private test directory yourself.

The command hook accepts a bounded JSON event on stdin and writes a single Claude protocol JSON object to stdout. A pass writes `{}` and leaves Claude's native permissions in force. In enforce mode, BLOCK and unsupported ASK produce `PreToolUse` deny; failure to contact the bridge, invalid response, unsafe local path, or missing eligibility state also denies a pre-tool call. Observe emits no veto or finding to agent-visible output. Only a `SessionStart` with `source: "startup"` can establish a new policy-free dormant session when no state exists. A session that starts while off retains only minimal eligibility metadata, not action payloads; after on, its first call establishes a fresh bridge generation without another `SessionStart`. Repeated starts retain prior eligibility, even after policy deletion. `SessionEnd` removes the session marker and releases bridge capacity; a lost marker on resume is unavailable, not dormant. A bridge restart does not reopen an ordinary previously live session. Start a new Claude session to reestablish it. Off is read from the existing cooperative owner control file, not from tool arguments.

These hooks do not implement a trusted Claude approval channel. ASK is denied in enforce mode. Tool descriptions and parameter schemas are not in these hook inputs and are not invented. Hook-supplied transcript paths are never opened. Result and lifecycle mapping is provisional pending actual-host verification. Claude decisions use the host-qualified cross-host archive; a missing result cannot certify execution. Hook invocations outside a live bridge, disabled or unstarted hooks, forced termination, host hook timeouts, execution outside exposed tool hooks and same-user tampering are not stopped by this code. The behavior of a killed or timed-out hook and parallel argument mutation must be tested on a pinned Claude version before calling enforcement supported.

## Owner control and status

Use the same control path for Pi, the bridge and hook clients. The default is `~/.tenet/control.json`, independent of `TENET_CLAUDE_DIR`. If you set `TENET_CONTROL_PATH`, set it in all three processes; Pi's explicit `controlPath` embedding option takes precedence. The file lives in an owner-only directory, has mode `0600`, and has no symlinked path components. The bridge socket and session markers live in the separate private `TENET_CLAUDE_DIR`. The CLI does not install hooks, start a bridge, change `TENET_MODE`, `TENET_POLICY` or `TENET_RECORDING`, or delete old recordings.

```sh
bun /ABSOLUTE/TENET/src/claude/cli.ts status
bun /ABSOLUTE/TENET/src/claude/cli.ts status SESSION_ID
bun /ABSOLUTE/TENET/src/claude/cli.ts off
bun /ABSOLUTE/TENET/src/claude/cli.ts on
```

`status` works while the bridge is stopped. Activation reports `on`, `off` or `unavailable` for corrupt/unsafe control. A never-configured control defaults to on. Mode is the CLI process's configured mode; bridge mode is separate and unknown when disconnected. Bridge `running` means its private socket answered the versioned status request, **not** that Claude hooks are installed or that enforcement coverage is verified. Coverage remains unverified until actual-host tests establish a supported version and hook configuration. Without a selected running session, policy readiness and session eligibility remain unknown; `status SESSION_ID` asks the bridge for that session's last readiness, if present. Capture status comes from the bridge writer's configuration and loss/pending counts, never from the CLI process's `TENET_RECORDING`. `on` means configured best-effort capture, not a guarantee of durable writes; degraded indicates observed loss. Without a bridge, capture is unknown unless activation is off or unavailable, which stops new capture but cannot recall queued writes.

`off` and `/tenet off` write the same cooperative owner-machine choice. Running Pi and the local bridge watch it while idle and recheck before assessments and pending releases. Off skips new assessments and capture and cancels pending work in those runtimes; a pending enforce call cannot get a late release, while observe never vetoes. `on` restores each process's configured mode and capture setting. Both operations can be repeated. CLI writes are durable before success is printed, but the CLI does **not** wait for cancellation acknowledgments from other processes. Another process can assess or release before it sees off; already dispatched work cannot be recalled. Queued archive writes may finish after off and old recordings remain. A corrupt or unreadable control file prevents new assessment/capture: enforce denies eligible pre-tool calls and observe permits them without claiming a pass. A safe malformed file can be replaced with `on` or `off`; unsafe permissions and symlink paths cause the write to fail without a success message.

This switch is not an OS boundary. Any agent or process with the owner's filesystem access can edit, replace or remove the control file, hook settings or socket state. Removing the control file lets a new process treat the choice as on. A bridge restart does not resume pending calls; reestablish a session before testing hooks again.

Offline verification: `bun test test/claude-bridge.test.ts` and `bun run typecheck`. Actual-host verification is blocked until a suitable Claude CLI is installed and can be run with isolated settings and harmless local effects. Do not substitute a protocol fixture for that gate.
