# TENET status in BB

Install from a stable TENET checkout with `bb plugin install /absolute/path/to/Tenet/bb-plugin-tenet-status`. For local development, `bb plugin build bb-plugin-tenet-status` from the repository root verifies the app, backend and host bundles. The plugin is read-only; install the TENET Pi extension and enable its own policy and recording separately. No Pi process is launched by the BB plugin.

Open a Pi thread and select **TENET rules** in the thread header (a **T** button on compact viewports). The popover stays summary-only. Its **Details** button opens a read-only list of flagged tool calls and the matching policy rule text. The call ID distinguishes repeated uses of one tool; a rule ID appears only when its text is unavailable. Coverage stays visible in one short line, with recording gaps in a disclosure. Severity, confidence and decision mechanics remain in the owner RPC but are not shown on this focused page. Refresh restarts at page one, including after a failed or stale next-page cursor. A flag is a recorded selected FAIL, not proof of a blocked or executed call. Non-Pi threads have no header action. The status view refreshes every ten seconds while open; the details page refreshes on demand. No indicator, per-call toast, transcript entry or agent tool is installed.

The plugin reads `~/.tenet/recordings` on the thread's BB machine by default. If TENET uses `TENET_RECORDING_DIR`, set the BB plugin's `recordingDirectories` setting to a JSON object keyed by BB machine ID, with an absolute archive path on each machine. For example: `bb plugin config tenet-status set recordingDirectories '{"host_abcdefgh1234":"/home/me/tenet-recordings"}'`. Use `bb plugin config tenet-status` to inspect the effective setting. This setting belongs to the owner, not to a thread or an agent. Host reads reject unsafe paths and files.

Only new Pi records with a valid BB-provided `BB_THREAD_ID` link to a thread. An already-running Pi process using an older TENET extension cannot gain this link retroactively; start a new BB Pi process with this extension and recording enabled. Historical recordings stay in TENET's standalone inspector and are not guessed into a BB thread. The machine is resolved by BB from the selected thread and its environment; no archive field grants access to another machine. A linked FAIL is the judge's recorded selected choice, including low-confidence choices. It is not proof of execution or a count of blocked calls. `partial` means linked calls were found, not complete monitoring; `unknown` means no linked records have been found so far, not a pass; `unavailable` means the machine or archive could not be read.
The host reader caches validated metadata. Each refresh limits directory scanning and shares its 256-stage/16-MiB parse budget across archive sessions. A cold archive may show only some linked calls at first; new stages in a dense session can take later refreshes to appear. The view reports gaps and updates on request. The header RPC returns only coverage, linked-call and validated-flag counts, and bounded gap codes. It does not send rule text, call IDs, decision fields, submitted actions or provider responses to BB. The separate owner-only detail RPC pages at five candidate calls, re-reads at most 64 stages / 16 MiB per candidate and sends only selected rule and call fields. It never sends raw actions, request payloads or provider responses. Historical unlinked recordings remain in TENET's standalone inspector. Gaps and writer loss prevent an all-clear claim.
